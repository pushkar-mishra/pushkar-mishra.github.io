1. Your Sessions Are Deleted After 30 Days

Start here, because this one costs people real work and almost nobody finds out until after it has happened.

Your sessions expire after 30 days by default

Claude Code removes local session transcripts you have not touched in the last 30 days, and cleanupPeriodDays is the setting that controls it. Open a side project you left alone for six weeks and the history is simply gone. Set cleanupPeriodDays in ~/.claude/settings.json to something much larger, and do it before you need it. Time Machine or File History might bail you out, but that is not a plan.

// ~/.claude/settings.json { "cleanupPeriodDays": 3650 // ~10 years. Retention is cheap. Lost context is not. }

The number you want is not "how long do I want history for?" It is "what is the longest gap between two visits to my least-active repo?" For anyone juggling several clients or a few dormant side projects, that gap runs to months. The 30-day default quietly assumes you live in one repository.

Claude Code Tip: renaming a project directory orphans its history

Transcripts are stored under ~/.claude/projects/ in a folder named after the project's absolute path with the separators flattened. Move ~/code/payments to ~/work/payments and Claude Code starts fresh in the new location while every prior session sits in a folder keyed to a path that no longer exists. Nothing is deleted, but /resume cannot see it, and the retention sweep will eventually collect it.

Look before you reorganise anything:

ls ~/.claude/projects/ # -Users-you-code-payments-api ← keyed to the OLD path # rename this to match the new flattened path after you move the repo

The Lab Notebook Analogy

A session is a lab notebook, not a chat log. It records what you tried, what failed, which constraint you hit on attempt four, and why you threw away the obvious approach. Six weeks later the code shows what you built. Only the session shows why the obvious design was wrong. Deleting it throws away the negative results, which are the most expensive and least reproducible thing you produced.

The resumption flags that are not --continue

Everyone knows claude -c. These three are the ones that change how you work:

🌿 --fork-session

Resume into a new session ID instead of writing over the original. Branch an investigation without destroying the trunk you branched from.

🔗 --from-pr 482

Jump back to the session tied to a pull request. A reviewer's question six days later lands in the context that produced the code.

🆔 --session-id <uuid>

Pin a deterministic session ID. This is what makes CI jobs able to resume their own prior runs.

One habit worth building: name anything that will outlive the afternoon. claude -n "rate-limiter-redesign" costs three seconds and saves ten minutes of picker archaeology later. Combined with a long retention window, ~/.claude/projects/ turns into a searchable record of engineering decisions, and arguably a more honest one than your commit history, since it still contains the paths you abandoned.

2. Which Settings File Actually Won

Most confusing Claude Code behaviour traces back to not knowing which settings file took precedence. A permission that auto-approves when you expected a prompt, an MCP server that will not appear, a hook that fires in one repo and not another: all the same root cause.

Settings Resolution Order

   HIGHEST PRECEDENCE
        │
   ┌────▼──────────────────────────────┐
   │  Enterprise managed policy         │  ← IT-controlled, cannot be overridden
   ├────▼──────────────────────────────┤
   │  Command-line flags                │  ← --model, --permission-mode, --settings
   ├────▼──────────────────────────────┤
   │  .claude/settings.local.json       │  ← per-developer, gitignored
   ├────▼──────────────────────────────┤
   │  .claude/settings.json             │  ← project, COMMITTED to the repo
   ├────▼──────────────────────────────┤
   │  ~/.claude/settings.json           │  ← your personal defaults
   └───────────────────────────────────┘
        │
   LOWEST PRECEDENCE

The split that keeps teams out of trouble is simple. Personal defaults and retention go in your home directory. Anything that should apply to every engineer on the repo, meaning permission policy, hooks, required MCP servers, shared agents and commands, goes in the committed project file. Machine-specific paths and experiments go in the gitignored local file.

Claude Code Tip: never put a credential in a settings file

apiKeyHelper takes a command that produces the key rather than the key itself. The secret stays in your OS keychain or your vault, and the settings file, which often gets committed, screenshotted and read by the agent, holds only a shell invocation.

// ~/.claude/settings.json { "apiKeyHelper": "/bin/sh -c 'security find-generic-password -s anthropic -w'" // or: "aws secretsmanager get-secret-value --secret-id claude --query SecretString --output text" }

For teams, forceLoginMethod pins everyone to one auth path so nobody ends up running on a personal key against a corporate repo.

Settings files fail silently in headless mode

In print mode, meaning -p or any run where stdout is not a TTY, settings files that fail validation are ignored without an error. A trailing comma in your project settings.json produces a friendly warning on your laptop and then quietly drops your entire permission policy in CI. That is a security control disappearing with no signal at all.

Claude Code Tip: validate settings JSON in pre-commit

Given the above, this is probably the highest-value ten-line hook in this article.

#!/bin/sh # .git/hooks/pre-commit for f in .claude/settings.json .mcp.json; do [ -f "$f" ] || continue python3 -c "import json,sys; json.load(open('$f'))" 2>/dev/null \ || { echo "✗ $f is not valid JSON, commit blocked"; exit 1; } done

The three bisection flags

These exist for the moment when your configuration is the problem. Between them they turn "Claude Code is acting weird" into a five-minute diagnosis.

🛟 --safe-mode

Starts with all customization off: CLAUDE.md, skills, plugins, hooks, MCP servers, custom commands, agents, output styles, keybindings. Auth, model and permissions still work. If the problem vanishes, it is yours.

🧪 --bare

Goes further and skips hooks, LSP, plugin sync, auto-memory, background prefetches, keychain reads and CLAUDE.md discovery. This is your clean room for a bug report.

🎚️ --setting-sources

Load only the tiers you name, from user, project and local. Three runs tell you which file is responsible without editing anything.

3. Permissions, Hooks and the Trust Boundary

Two things live under this heading and people routinely conflate them. Containment is about limiting what the agent can touch, and it is configuration. Trust is about recognising that every file, tool result, web page and MCP response entering the context is untrusted input that may contain instructions, and that is architecture.

Sort permissions by reversibility, not by danger

The deny list beats allow, which makes it the right home for anything that must never reach a context window. Once a secret is in the transcript it is on disk, and it may well survive into a compacted summary.

The tier people underuse is ask. It lets you run in acceptEdits for speed while still forcing a human decision on the few operations that leave your machine or touch production. Reversibility is the criterion that matters. Edits can be undone. Pushes, publishes, applies and deletes cannot.

// .claude/settings.json (commit this) { "permissions": { "deny": ["Read(./.env*)", "Read(./secrets/**)", "Read(~/.aws/**)", "Read(~/.ssh/**)"], "ask": ["Bash(git push:*)", "Bash(npm publish:*)", "Bash(terraform apply:*)", "Bash(kubectl delete:*)"], "allow": ["Bash(npm test:*)", "Read(./src/**)", "Edit(./src/**)"], "defaultMode": "acceptEdits" } }

Claude Code Tip: a deny rule is a prefix match, not a command name

This catches nearly everyone once. Bash(git:*) blocks git status and git diff right along with git push, and the resulting behaviour reads as the model being unhelpful rather than as a rule misfiring. Write rules at the specificity you actually mean, and check with /permissions before blaming the model.

✗ "deny": ["Bash(git:*)"] // blocks ALL git, including reads ✓ "deny": ["Bash(git push --force:*)", "Bash(git reset --hard:*)"] ✓ "ask": ["Bash(git push:*)"] claude --debug hooks,permissions # shows which rule matched

Claude Code Tip: lock out permission bypass at the policy layer

A deny list is only as good as the flag that skips it. disableBypassPermissionsMode makes --dangerously-skip-permissions unavailable rather than merely frowned upon. Set it in enterprise managed policy, where it sits above every other tier and no local file can override it.

// enterprise managed policy { "permissions": { "disableBypassPermissionsMode": "disable" } }

The same logic applies in reverse to disableAllHooks. It is a useful debugging switch, which makes it a useful attack switch too. If a security guarantee of yours depends on a PreToolUse hook, understand that anyone who can set that key has switched your guarantee off.

Hooks are rules; prompt text is a request

This distinction is worth internalising. A line in CLAUDE.md saying "always run the linter" is advice the model weighs against everything else in context. A PostToolUse hook that runs the linter is a deterministic guarantee executed by the harness. Anything that must happen every time belongs in a hook.

EventFiresWorth using for
PreToolUseBefore a tool runsBlocking dangerous commands, scanning diffs for secrets. A blocking exit stops the call and returns your message to the model.
PostToolUseAfter a tool succeedsFormatting, type checking, running affected tests, audit logging.
UserPromptSubmitBefore your message is processedInjecting dynamic context such as the current ticket or deploy-freeze status, without bloating the static prompt.
PreCompactBefore compactionPersisting decisions to a file before they get summarised away. The most underrated hook here.
SessionStart / SessionEndSession boundariesSnapshotting git state, exporting transcripts to a team knowledge base.

A Secret-Scanning PreToolUse Hook

Match a PreToolUse hook to Edit|Write and pipe the proposed content through gitleaks or a regex battery. If it spots an AWS key, a JWT or a private key header, exit with the blocking status and a message like "Refusing write: credential-shaped string at line 42. Use environment variables." The model reads that and corrects itself. Credential leakage is now structurally impossible rather than culturally discouraged, and the same hook covers the engineer who never read your security wiki.

Prompt injection is a supply-chain problem

This is the part experienced engineers tend to underweight. When Claude Code fetches a web page, reads a dependency's README, pulls an issue body through MCP or ingests a log file, that content lands in the same context as your instructions. A well-crafted string in a third-party file is an instruction the agent may act on.

🔐 MCP servers are dependencies

An MCP server can read your context and take actions. Vet the source, pin the version, scope its tools. A committed .mcp.json means the same vetted set for everyone and additions go through review.

🧱 Split read scope from write scope

Read broadly, edit narrowly. Config, CI definitions and infrastructure files are exactly where an injected edit does the most damage.

🚧 Restrict the toolset for untrusted work

--tools "Read,Grep,Glob" is blunt and effective. An agent with no WebFetch tool cannot be talked into using one.

Claude Code Tip: never auto-approve project MCP servers

enableAllProjectMcpServers connects every server a repo declares in its .mcp.json. Convenient for a repo you own, and a genuine hole for one you just cloned, since auto-approving whatever a repository declares is much the same as running its install scripts unread. Keep it off and allowlist by name. The explicit list doubles as a record of which integrations have actually been reviewed.

{ "enableAllProjectMcpServers": false, "enabledMcpjsonServers": ["sentry", "postgres-readonly"] }

4. The Built-In Sandbox (and Credential Masking)

Claude Code ships an OS-level sandbox, and a surprising number of teams are still solving this problem with disposable containers because they do not know it is there. It uses Seatbelt on macOS, bubblewrap on Linux, and a dedicated user plus network filters on Windows. Bash commands run inside it by default, and it controls both which paths they can touch and which hosts they can reach.

Run /sandbox to see and manage the current restrictions. On some platforms you will need /sandbox install once, which sets up the sandbox user and network filters and needs an elevation prompt.

What the Sandbox Controls

                    ┌──────────────────────────────┐
   bash command ───▶│      OS SANDBOX              │
                    │                              │
                    │  filesystem ── allowWrite    │──▶ writes outside the
                    │              ── denyRead     │    allowlist are blocked
                    │              ── denyWrite    │
                    │                              │
                    │  network ──── allowedDomains │──▶ hosts not listed are
                    │           ──── deniedDomains │    denied, not prompted
                    │                              │
                    │  credentials ─ deny  (unset) │──▶ the command sees a
                    │              ─ mask  (fake)  │    SENTINEL, not the secret
                    └──────────────────────────────┘
                                  │
              allowUnsandboxedCommands: false
                     ⇒ dangerouslyDisableSandbox is ignored entirely

Credential masking is the feature to know about

Everything above is useful, but this is the part almost nobody has found. Under sandbox.credentials, environment variables and files each take an access mode of deny or mask. deny unsets the variable or blocks the read. mask is the interesting one: the sandboxed command is shown a sentinel value instead of the real secret, and for files you get a sentinel-substituted copy, either whole-file or only the spans you capture with extract.

The practical difference matters. Denying Read(./.env) stops the file being read at all, which also stops the command that legitimately needed it from working. Masking lets the command run normally while never exposing the real value. For anything where the agent needs to exercise a code path that touches credentials without ever seeing them, this is what you want.

// .claude/settings.json { "sandbox": { "enabled": true, "network": { "allowedDomains": ["registry.npmjs.org", "*.internal.example.com"], "deniedDomains": ["*.pastebin.com"], "allowManagedDomainsOnly": true // deny unlisted hosts outright, do not prompt }, "filesystem": { "allowWrite": ["./build", "./.cache"], "denyRead": ["./secrets/**"] }, "credentials": { "envVars": { "AWS_SECRET_ACCESS_KEY": { "mode": "mask" }, // sandboxed cmds see a sentinel "GITHUB_TOKEN": { "mode": "deny" } // unset entirely }, "files": { "~/.aws/credentials": { "mode": "mask" } } }, "allowUnsandboxedCommands": false, // dangerouslyDisableSandbox becomes inert "autoAllowBashIfSandboxed": true, // sandboxed commands need no extra prompt "failIfUnavailable": true // if the sandbox cannot start, refuse to run } }

Decide whether the sandbox fails open or closed

The sandbox does not always come up. A platform without support, a missing filter install, a nested or restricted environment: any of these can leave it unavailable, and failIfUnavailable is what decides the outcome. Set it to false and commands run unsandboxed instead. Leave it true and they are refused.

This is the setting that determines whether the rest of §4 is a guarantee or a preference. Locking down allowUnsandboxedCommands while the sandbox can silently fail open buys you much less than it appears to, and the failure is quiet, because nothing announces that today's session is running without the containment you configured. Fail closed for anything sensitive and treat a refusal as the signal to go fix the sandbox.

Claude Code Tip: allowUnsandboxedCommands: false is the real lock

Individual bash calls can normally escape with a dangerouslyDisableSandbox parameter. Set allowUnsandboxedCommands to false and that parameter is ignored completely, so every command must run sandboxed with no exceptions. This is a harder guarantee than disableBypassPermissionsMode, because it constrains what the agent can do inside a session rather than how the session was started. Put it in managed policy for anything sensitive.

excludedCommands is the pressure valve. List the specific commands that genuinely cannot work sandboxed, rather than turning the whole thing off because one tool broke.

Use $TMPDIR, never /tmp

Under the sandbox, TMPDIR is set to the sandbox-writable temp directory and /tmp is not writable. Any hook, script or slash command of yours that hardcodes /tmp will fail in a way that looks like a permissions bug. Claude Code's own guidance to the model is explicit about this, and your tooling should follow the same rule.

Where this leaves the sandbox hierarchy

The old advice was to reach for a disposable container whenever you wanted real isolation. With the built-in sandbox that is usually more machinery than the job needs. A more accurate ladder now looks like this:

PostureSetupFits
Sandbox on, domains allowlisted, credentials maskedsandbox.enabled plus a network allowlist and credential modesThe daily default. Real containment with no container to manage.
Sandbox plus locked policyAdd allowUnsandboxedCommands: false, failIfUnavailable: true and disableBypassPermissionsMode in managed policyRegulated environments, shared machines, anything where you cannot rely on individual discipline.
Read-only toolset, plan mode--tools "Read,Grep,Glob" --permission-mode planReviewing an untrusted PR or an unfamiliar dependency. Nothing can execute or be written.
Disposable container, permissions bypassedThrowaway VM or CI runner, no credentials, no egressStill the right answer for fully autonomous long runs, but no longer the first thing to reach for.

5. Where the Context Window Actually Goes

Most people's mental model is wrong in the same way. They picture the conversation as the cost. In a real agentic session the conversation is a rounding error, and the cost is tool result payloads, file contents, and the fixed overhead you pay on every single request.

Anatomy of One Request's Input Tokens

 ┌──────────────────────────────────────────────────┐
 │  SYSTEM PROMPT + TOOL DEFINITIONS                 │  ← paid EVERY request,
 │  • built-in tool schemas                          │    grows with each MCP
 │  • every MCP server's tool schemas   ⚠️ the tax    │    server you connect
 ├──────────────────────────────────────────────────┤
 │  CLAUDE.md (project + user + imports)             │  ← paid EVERY request
 ├──────────────────────────────────────────────────┤
 │  DYNAMIC SECTIONS                                 │  ← cwd, env, git status,
 │  (cwd, environment, memory paths, git status)     │    memory paths
 ├──────────────────────────────────────────────────┤
 │  CONVERSATION HISTORY                             │
 │  ├─ your messages          (small)                │
 │  ├─ assistant messages     (small)                │
 │  └─ TOOL RESULTS           (ENORMOUS) ◄───────────┼─ the real cost centre
 └──────────────────────────────────────────────────┘
             │
             ▼
   Everything above the first changed byte is CACHE-READ (~10% cost).
   Everything from that byte onward is FULL PRICE.

The prefix-cache rule that governs everything

Prompt caching is a prefix match. The cached span runs from the start of the request to the first byte that differs from last time. Change one byte early and everything after it gets reprocessed at full price. That single fact explains most surprising cost behaviour:

💥 Editing CLAUDE.md mid-session

It sits near the front of the prefix, so editing it invalidates the cache for the entire conversation after it. Batch memory edits and do them at a session boundary.

💥 Adding an MCP server mid-session

Tool definitions render before everything else. Adding, removing or reordering one rebuilds the whole prefix. Configure MCP at session start and leave it alone.

💥 Switching models mid-session

Caches are model-scoped, so a mid-session switch starts from zero. If you want a cheaper model for a sub-task, delegate to a subagent instead.

✅ Long tool loops

Counter-intuitively the healthiest pattern. Appending results at the end never invalidates the prefix, so a hundred-step loop reads cache on every step.

The Flag Almost Nobody Knows: --exclude-dynamic-system-prompt-sections

By default, per-machine details like your working directory, environment info, memory paths and git status are embedded in the system prompt, right at the front of the cacheable prefix. That means your prefix is unique to your machine and to your current git state. This flag moves those sections out of the system prompt and into the first user message instead, which dramatically improves cross-user prompt-cache reuse. For a platform team running Claude Code across dozens of similar CI jobs, or a shared gateway serving many engineers on one repo, that is a real line item, and it costs one flag. It only applies with the default system prompt.

The MCP tax

Every MCP server you connect injects its full tool schemas into every request, permanently. A rich server can carry dozens of tools with detailed descriptions and JSON schemas. Five of them, casually enabled and never audited, can eat a five-figure token count before you have typed anything.

Run /context and look at the breakdown. Most people doing this for the first time find their largest single line item is a set of MCP tools they used once, months ago. The fix is to enable servers per project through a committed .mcp.json rather than globally. A repo that never touches your ticketing system should not be paying for its schemas.

Claude Code Tip: four environment variables that cap runaway costs

Asking the agent to keep output short is advice. These are ceilings the harness enforces, and they defend against the case where one command, whether a verbose test run or a chatty MCP server, dumps tens of thousands of tokens into a context you then carry for the rest of the session.

{ "env": { "BASH_MAX_OUTPUT_LENGTH": "20000", // truncate huge command output "MAX_MCP_OUTPUT_TOKENS": "8000", // cap chatty MCP tool responses "CLAUDE_CODE_MAX_OUTPUT_TOKENS": "16000", // ceiling on model output per turn "MAX_THINKING_TOKENS": "8000" // bound reasoning depth } }

Set these once in your user settings and they apply everywhere. BASH_MAX_OUTPUT_LENGTH alone tends to pay for the exercise the first time somebody runs a test suite without a quiet flag.

Claude Code Tip: read /context as a ranked list of suspects

Most people glance at /context, note that the number is big, and move on. The value is in which line item is largest, because each diagnosis has a completely different fix and applying the wrong one is wasted effort.

MCP tools dominate → configuration problem. Disconnect servers. Prompting will not help. Tool results dominate → your commands are too verbose. Fix them in CLAUDE.md. System prompt / memory → CLAUDE.md has accreted. Prune it. Conversation history → you needed /clear two tasks ago.

Worth knowing alongside it: /usage is not the same as /cost. /cost reports spend for the session, /usage shows you where you stand against your limits. If you are hitting ceilings rather than budgets, the second one is the one you want.

6. Essential Token Management Strategies

The previous section covered mechanics. This is the operational checklist, in rough order of return on effort.

  1. Clear and Compact

    You already know to use /clear between unrelated tasks and /compact on a long but still-relevant thread. The detail people miss is that compact takes an argument. Bare /compact lets the model decide what matters. Steering it changes what survives, and rejected approaches are the first thing a generic summary throws away and the first thing you will wish you had kept.

    /compact keep the retry semantics, the decision to use exponential backoff, and every approach we rejected and why claude --autocompact 200000 # tune the auto-compact window (100k–1M)
  2. Manage Integrations

    Disconnect idle MCP servers. Their tool definitions are re-sent with every single message, so a server you used once in March is still billing you on every request today.

    Scope them per project rather than globally. enabledMcpjsonServers allowlists explicitly, and when you want a guaranteed-clean set for one session, --strict-mcp-config ignores every other MCP configuration source.

    claude mcp list # audit what is connected claude --strict-mcp-config --mcp-config ./ci.mcp.json # load ONLY these { "env": { "MAX_MCP_OUTPUT_TOKENS": "8000", "MCP_TIMEOUT": "10000" } }
  3. Optimise Configuration

    Keep CLAUDE.md short and high-level. It is re-sent on every request forever, so treat 100 lines as a hard budget and push conditional detail into @imports.

    To stop build folders, lockfiles and env files loading, use permissions.deny with Read() rules. There is no .claudeignore file. It is a persistent myth borrowed from other tools. The deny list is the real mechanism, and it is better anyway, because the harness enforces it and it constrains the agent's own exploration rather than just yours.

    { "permissions": { "deny": [ "Read(./node_modules/**)", "Read(./dist/**)", "Read(./build/**)", "Read(./.next/**)", "Read(./coverage/**)", "Read(./**/*.lock)", "Read(./**/*.min.js)", "Read(./src/generated/**)" ] } }
  4. Targeted Context

    @-mention the files you already know are relevant instead of letting the agent discover them, and reference documents by path rather than pasting them.

    The economics are stark. Letting the agent find a file costs a grep, a directory listing, two or three speculative reads, and then the file. Naming it costs the file. A pasted document is re-sent at full price on every subsequent turn, whereas a referenced one is read once. Spending your own knowledge of the codebase is free. Making the agent rediscover it is not.

    ✗ "Find the retry logic and fix the backoff" ✓ "In @src/infra/clients/http.ts, the backoff around line 80 is linear. Make it exponential with jitter."
  5. Monitor Usage

    Run /context and /cost regularly, and /usage when you are bumping into limits rather than budgets. You cannot optimise what you have not measured, and the answer is almost never what the team assumes.

    claude -p "..." --max-budget-usd 2.00 # hard cap for anything autonomous

Claude Code Tip: the two strategies that are not on anyone's list

Delegate the reading. The levers above reduce what enters your context. Subagents move the reading into a separate context window entirely, so those tokens are spent once and then discarded. "Use a subagent to find every place we construct an HTTP client" costs you the twelve-line answer rather than the fifty files. On a large repo this often beats everything else combined, and it is the one strategy that gets more valuable as the codebase grows.

Use Skills for progressive disclosure. A skill in .claude/skills/<name>/SKILL.md keeps only its short description in context, and the full body loads when the task actually calls for it. Anything you are currently keeping in CLAUDE.md "just in case" is a skill in disguise, and moving it converts a permanent per-request cost into an occasional one. See §11 for the shape of the file.

7. Permission Modes and Rewind: Controls Worth Rewiring Your Habits For

These get mentioned in passing constantly and explained almost never, which is a shame because between them they change how much risk you can take.

The four modes on Shift+Tab

Shift+Tab cycles the permission mode mid-session. Most people find two of these and never meet the other two.

ModeBehaviourReach for it when
defaultAsks before every editUnfamiliar territory, or you want to see each change as it happens.
accept editsEdits freely, asks for commandsThe daily driver for work you understand.
planResearches and proposes, never touches filesBig refactors, and anything you do not trust.
autoClaude decides what is safe, backed by a classifierLong unattended runs where stopping to ask defeats the point.

Auto mode is the one worth knowing about, because it is not simply a looser version of accept-edits. A separate classifier evaluates each action, and it is deliberately fail-closed: if the classifier cannot be reached or its answer cannot be parsed, the call is held back rather than allowed through. Those outcomes are distinct from a policy decision, which matters when you are reading logs and trying to work out whether something was denied or merely never evaluated. Note also that auto mode ignores Bash allow rules entirely, so a permission rule you rely on elsewhere does not carry over into it.

The Shift+Tab cycle shows four modes, but --permission-mode accepts six: default, acceptEdits, plan, auto, dontAsk and bypassPermissions, plus manual. If you are scripting Claude Code, work from the flag list rather than what the cycler shows you.

Plan mode

Plan mode lets the agent read and reason but not write or execute. It investigates, then comes back with a plan you approve or reject before anything happens.

It is worth treating as two separate tools. As a workflow control, it is how you keep an agent from confidently implementing the wrong design: the cost of a bad plan is a paragraph you disagree with, rather than eleven files you have to unpick. As a security control, it is the safest way to look at code you do not trust, because nothing can execute while you read.

# Investigate an unfamiliar or untrusted codebase with no ability to act claude --permission-mode plan --tools "Read,Grep,Glob" # The pattern that pays for itself on anything non-trivial: # 1. plan mode → agree the approach # 2. acceptEdits → let it run # 3. review the diff, not the summary

The habit worth building is using it for anything touching auth, payments, migrations or infrastructure, regardless of how small the change looks. Those are the areas where a confident wrong answer is most expensive and where the plan is most likely to reveal a wrong assumption early.

Rewind

Claude Code checkpoints your files before every edit, and /rewind rolls back to any prior state. Double-tap Esc gets you there quickly.

The part that is easy to miss: rewind covers code, conversation, or both, and you choose which. That makes it two tools rather than one. Rolling back files is the obvious use. Rolling back only the conversation is the one people never think to reach for, and it is how you escape a thread that has gone somewhere unproductive without discarding the work that came out of it. The reverse is just as useful when the reasoning was sound but the edits were not.

Either beats asking the agent to undo its own work, which depends on it correctly remembering everything it touched. Treat git commit as your coarse checkpoint and rewind as the fine one. Between them, abandoning an approach becomes cheap, and that is what makes aggressive experimentation reasonable in the first place. Most people discover rewind the session after the one where they needed it.

8. Greenfield vs. Inherited Codebases

The two situations need opposite instincts. On a new project you can design the context surface before it grows. On an inherited one you cannot change the surface at all, only control how much of it enters any given session.

New project: design the surface early

CLAUDE.md is paid on every request forever, and that constraint should discipline it hard. It is not documentation and not a style guide. It is the set of facts that change the agent's behaviour: canonical commands, architectural invariants, the two or three conventions that are not obvious from reading the code, and the directories that are off-limits. Nothing the agent could trivially infer.

Three decisions on day one that keep paying:

🤫 Canonical quiet commands

Put the filtered, quiet test command in CLAUDE.md from the start. Every future session inherits the saving, and retrofitting this once the agent has learned verbose habits is oddly hard to undo.

📐 Plan the architecture, do not autocomplete it

The design conversation before any file exists is the highest-leverage use of a strong model. Getting boundaries right saves more than every micro-optimisation here, because it prevents the refactor.

🗄️ A PreCompact hook for decisions

Early architectural decisions are exactly what summarisation flattens. Append them to docs/decisions.md before compaction and you have turned transient context into an ADR log.

How CLAUDE.md goes wrong

The usual failure is accretion by incident. The agent does something annoying, someone appends a rule. Six months on the file is 600 lines of narrow prohibitions, each traceable to one bad afternoon, and the agent is navigating a maze of special cases instead of a coherent principle. Prune on a schedule. If a rule cannot be justified by someone who was not there when it was written, delete it and see what breaks.

Inherited codebase: never let it explore when you could just tell it

In a repository with thousands of files, discovery is where the tokens die. Ask an agent to "fix the retry logic in the payment flow" with no map and it will grep, read, follow imports, read more, and burn tens of thousands of tokens before writing a line. The fix is a navigation layer in CLAUDE.md. Not documentation of what the code does, but a directory of where things live.

# Codebase Map - HTTP handlers: src/api/**/handler.ts - Business logic: src/domain/** (no I/O here, keep it pure) - Persistence: src/infra/repo/** - External clients: src/infra/clients/** (retry/backoff lives here) - Generated code: src/generated/** DO NOT EDIT. Regenerate: `npm run codegen` ## Conventions that are not obvious - All money is `bigint` minor units. Never float. - `src/domain` must not import from `src/infra`. Enforced by `npm run lint:deps`. - Anything under `legacy/` is frozen. Changes go in `src/` behind an adapter.

That block costs maybe 200 tokens a request and routinely saves tens of thousands. The "DO NOT EDIT" and "frozen" markers alone head off a whole class of expensive, well-intentioned mistakes.

The Scout-Then-Build Pattern

Turn one: "Use a subagent to find every place we construct an HTTP client. Report the file paths, the retry configuration at each, and any that differ from the default." The subagent reads fifty files in its own context and hands back twelve lines. Turn two: "Standardise those onto the shared client." Your main context now holds a twelve-line map and the task rather than fifty files. On a large repo this regularly turns a session that would have compacted twice into one that never compacts at all, which also means the model never loses its early decisions to summarisation.

9. Microservices and Multi-Repo Workflows

This is where most teams' practice quietly breaks down, because the tool's defaults assume one repository and microservices assume the opposite. A change to a payment flow touches the gateway repo, the payments service, a shared contracts repo and probably Terraform. By default the agent sees one of them.

TopologySetupRight when
Single-serviceStart in one repoThe change is genuinely local. Should be your default, because most changes really are.
Anchored multi-repo--add-dir ../contracts ../gatewayOne service is clearly the subject and the others are supporting context.
Workspace rootA parent directory holding all the repos as siblings, with its own CLAUDE.mdCross-cutting work: a protocol bump, a shared library upgrade, a tracing rollout across eight services.

The workspace-root CLAUDE.md is the highest-leverage file you will write

Not because of what it documents, but because it encodes the thing no single repository can know, which is the shape of the system. Dependency direction, which service owns which data, where the contract lives, deploy ordering, and which changes need a coordinated release.

# Platform Topology ## Call graph (direction matters, never introduce a reverse edge) client → gateway → payments-svc → ledger-svc ↘ notifications-svc ## Ownership - `payments-svc` owns the `payments` schema. Nothing else writes to it. - `ledger-svc` owns `ledger`. Payments reads it ONLY via the gRPC API. ## Contracts - Source of truth: `contracts/proto/**`. Generated stubs are committed, never hand-edited. - A breaking change requires: contracts PR → consumer PRs → producer PR. In that order. ## Coordinated-release triggers Any change touching `contracts/proto/payments/v1/**` needs a release plan. Flag this to me rather than proceeding.

That last section is the one platform engineers appreciate immediately. It converts tribal release knowledge into something the agent will respect, and turns "the agent broke prod because it did not know about deploy ordering" into a non-event.

Claude Code Tip: --add-dir grants access, not attention

Adding a directory makes it reachable. It does not tell the agent the directory matters or what is in it. The common disappointment, "I added the contracts repo and it still did not check the schema", is exactly this gap. Pair every added directory with a line in CLAUDE.md explaining its role and the behaviour changes immediately.

claude --add-dir ../contracts ../gateway # ...and in the workspace CLAUDE.md: # ../contracts → source of truth for all inter-service schemas. # ALWAYS check here before changing a request/response shape. # ../gateway → the only caller of payments-svc. Check its client before # altering any public endpoint.

Claude Code Tip: keep the shell anchored across repos

With several repos mounted, a cd inside one bash call silently changes the working directory for later commands, and the agent then runs your test suite from the wrong service. CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR forces every command back to the project root, which turns a whole class of confusing cross-repo failures into a non-issue.

{ "env": { "CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR": "1" } }

Parallelism: worktrees and background agents

Multi-repo work invites parallel sessions, and several terminals in one working tree produces conflicting edits and mutual confusion. Git worktrees solve it properly, and Claude Code has first-class support.

claude --worktree payments-retry # isolated tree + branch + session claude --worktree contract-v2 --tmux # with a tmux session (iTerm2 panes if available) claude --bg -p "run the contract audit" # background agent, returns immediately claude agents # manage running background agents

The Assembly Line Analogy

Three agents in one working tree is three mechanics reaching into the same engine bay. Three worktrees is three engines on three bays with a shared parts shelf, which is the contracts repo. Setting up the bay costs almost nothing next to untangling three sets of half-finished edits, and worktrees make "abandon this attempt entirely" cheap, which is what makes parallel exploration viable at all.

Contract-first is what keeps it honest

The failure mode in agentic multi-repo work is drift. The agent changes the producer, the consumer's stub is stale, tests pass in both repos independently, and integration breaks. The countermeasure is structural rather than something you can prompt your way out of.

1️⃣ Contract change first

Write it into the workspace CLAUDE.md that any cross-service change starts in the contracts repo, so the agent propagates from one source of truth rather than inferring shape from one side.

2️⃣ A contract-auditor subagent

One subagent whose only job is comparing producer and consumer against the spec. Cheap, isolated context, catches exactly this failure.

3️⃣ Regenerate, never hand-edit

Deny Edit on generated stub directories in every repo. The agent is entirely capable of "fixing" a generated file, which works locally and silently diverges from the spec.

4️⃣ Integration test as the gate

Unit tests passing in both repos proves nothing about the seam between them. Wire the cross-service tests into a hook or a slash command.

10. Debugging Claude Code Itself

When the agent misbehaves, meaning a hook that will not fire, an MCP tool that never appears, permissions prompting when they should not, or latency out of nowhere, the debug flag has a category filter almost nobody uses.

claude --debug api,hooks # only these categories claude --debug '!1p,!file' # everything EXCEPT first-party noise and file ops claude --debug-file /tmp/cc.log # write to a file (implicitly enables debug mode)

The negation syntax is the useful half. Raw debug output is overwhelming, and subtractive filtering, where you turn everything on then silence what you know is irrelevant, converges on the signal far faster than guessing which category to enable.

The bisection ladder

  1. Does it reproduce in --safe-mode?

    All customization off. If the problem disappears, it is your configuration, and you have eliminated the entire product surface in one command.

  2. Narrow by tier with --setting-sources

    Load only user, then only project, then only local. Three runs identify the file without you editing anything.

  3. Isolate MCP with --strict-mcp-config

    With an explicit --mcp-config, this loads only the servers you name. Fastest way to find out whether a server is the culprit, and which one.

  4. Drop to --bare for a clean room

    Skips hooks, LSP, plugin sync, auto-memory, prefetches, keychain reads and CLAUDE.md discovery. This is the baseline for a bug report, because it proves the issue is in the tool rather than your environment.

  5. Check for a deny rule matching too broadly

    A surprising share of "the agent will not do X" reports are a prefix rule catching more than intended. The debug output names the rule that matched.

Hooks fail silently in ways that look like model behaviour

A hook with a bad path, a missing execute bit, or a dependency that is not on PATH in the hook's environment produces symptoms that read as the model ignoring instructions. The formatter "did not run". The validator "let it through". Test every hook command standalone in a clean shell before wiring it up, and have it log somewhere. --debug hooks shows the invocation and its exit status, which resolves this in seconds once you know to look.

Claude Code Tip: capture a reproducible log before you report anything

--debug-file turns on debug mode and writes to a path, so you can reproduce an issue and hand someone the artifact rather than describing it. Combine it with --bare and a fixed --session-id so the run stays addressable afterwards.

claude --bare \ --debug-file /tmp/cc-repro.log \ --session-id 3f2b8c10-7d4e-4a91-b5c2-9e1f0a6d8b34 \ -p "reproduce the failing case"

11. Configuration Recipes

Four artifacts. Each is small, each gets committed, and each replaces something a human would otherwise have to remember.

A read-only subagent

Subagents live in .claude/agents/. The design choice that matters is restricting tools, because an explorer that cannot edit will not accidentally edit, and a narrower toolset also means a smaller schema in its context.

--- name: codebase-scout description: Read-only investigator. Use for "where is X", "how does Y work", "find every place that Z". Returns findings, never edits. tools: Read, Grep, Glob model: sonnet --- You investigate and report. You never modify files. Return findings in this shape: 1. Direct answer, two or three sentences. 2. Evidence: file:line references for every claim. 3. Anything surprising you found on the way. 4. What you could NOT determine, stated plainly. Be exhaustive in your reading and ruthlessly brief in your output. The caller's context window is the scarce resource, not yours.

Note the model choice. Scouting is reading and extraction rather than deep reasoning, so a faster model does it well, and the delegation keeps your main thread on the strong model without paying for it to read fifty files.

A skill, for anything you keep repeating

Skills live in .claude/skills/<name>/SKILL.md. Only the frontmatter description sits in context by default, and the body loads when the task matches. That progressive disclosure is what makes them different from CLAUDE.md content, which you pay for always.

--- name: add-endpoint description: How to add an HTTP endpoint in this service. Use whenever adding, modifying or removing a route, handler or its validation schema. --- # Adding an endpoint 1. Define the schema in `src/api/schemas/` first. Never inline it in the handler. 2. Handler goes in `src/api/<resource>/handler.ts`, thin, no business logic. 3. Business logic goes in `src/domain/<resource>/`, pure, no I/O. 4. Register in `src/api/routes.ts`. Alphabetical order, we lint for it. 5. Contract test in `tests/contract/<resource>.spec.ts` is mandatory. ## Gotchas - Auth middleware is opt-out, not opt-in. Public routes need `{ public: true }`. - Anything returning money must use the `MoneySchema`, never a raw number.

Anything in your CLAUDE.md that starts with "when you are doing X..." is a skill in disguise. Moving it converts a permanent per-request cost into an occasional one, and the skill can be much longer than you would ever allow in CLAUDE.md.

A slash command that encodes a workflow

Commands live in .claude/commands/. The ! prefix runs a shell command and injects its output, @ references a file, and $ARGUMENTS captures what you typed.

--- description: Review the current branch's diff against main allowed-tools: Bash(git diff:*), Bash(git log:*), Read, Grep --- Current diff against main: !`git diff main...HEAD` Project conventions: @docs/conventions.md Review the diff above. Focus specifically on: $ARGUMENTS For each finding give file:line, the concrete failure scenario, and a suggested fix. Rank by severity. If you find nothing significant, say so plainly rather than manufacturing findings.

Invoked as /review-branch concurrency and error handling. The shell commands run before the model sees anything, so the diff is already in context, with no tool round-trip and no negotiation about which commands to run.

A hook that makes a rule structural

{ "hooks": { "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [ { "type": "command", "command": "npx prettier --write \"$CLAUDE_FILE_PATHS\" 2>/dev/null || true" }, { "type": "command", "command": "npx tsc --noEmit 2>&1 | head -40" } ] }], "PreCompact": [{ "hooks": [{ "type": "command", "command": ".claude/scripts/persist-decisions.sh" }] }] } }

The formatter guarantees consistency with no prompt text at all. The type check surfaces errors while the agent still has the change in working context, rather than at the end of the session when rebuilding that context is expensive. Note the || true: a hook that fails loudly on an unformattable file becomes noise you learn to ignore, which defeats the point.

The Final Perspective

The instinct with a capable coding agent is to get better at asking. That instinct is half right and mostly misdirected. The people getting disproportionate returns are not writing better prompts, they are engineering the environment the agent works in. A tight CLAUDE.md that costs 200 tokens and saves 20,000. Hooks that make quality structural instead of aspirational. Permissions sorted by reversibility. A sandbox that masks credentials rather than hiding files. Subagents that keep the main context clean. Retention set so six months of hard-won context survives. None of this is really about the model. It is ordinary systems engineering, applied to a new kind of process, and the prompt is the least durable artifact you will produce.

"The best prompt is the one you never have to write, because the environment already encodes the answer."
